Flock Calendar

A care schedule for layer farms that asks a few setup questions, generates a calendar of recurring flock care, and lets the farmer see and check off what's due — so the routine lives in the app, not in his head.

Status: approved Markdown is canonical · this page is a companion

How it fits together

Storage drives everything: empty storage → setup; otherwise load batches/rules and draw the calendar.

How this works, in plain language

Flock Calendar is a phone app that holds a layer farm's care routine so Monday doesn't have to remember it himself.

When he first opens the app, he answers a short setup questionnaire: what kind of birds he has, how many, how old they are, whether he's a student or worker, how many times a day he feeds and checks the birds, and when vaccines/deworming happen. The app takes those answers and a built-in standard poultry schedule (age-based rules for vaccines, deworming, cage cleaning, water changes) and generates a calendar. Every date on the calendar shows what's due that day.

Monday opens the app and sees a calendar. He taps a date, and a list opens showing that day's tasks plus the next few days — things like feed, water, check up, pick eggs, cage cleaning, deworming, vaccines. Each task has a checkbox. When he checks one off, it's saved so it won't show up again tomorrow. If it's a multi-day task like deworming, checking day 1 off moves to day 2.

He can add another batch of birds later, or add a custom task to any day. Everything is saved on his phone, so when he closes and reopens the app, the schedule and his progress are still there. No accounts, no internet needed, no backend — it all lives in a small file on his phone.

The core journey through the system

  1. Monday opens the app. The Setup screen shows if nothing is saved yet (src/app/setup.tsx). He answers the questionnaire.
  2. The app merges his answers with the built-in poultry schedule (src/schedule/poultry.ts) into per-batch care rules (src/schedule/build.ts) and saves them (src/storage/store.ts).
  3. He's taken to the calendar (src/app/index.tsx). Each date shows how many tasks are due, computed live from the rules.
  4. He taps a date → the day list (src/app/day/[date].tsx) opens: that day's tasks plus the next 7 days.
  5. He checks a task off → it's saved to completions (src/storage/store.ts) and drops off the pending list. A multi-day task advances to its next day.
  6. He can add a batch or a custom task → saved as new rules/entries.
  7. He reopens the app → AsyncStorage loads → same calendar, same progress.

Where it runs and how someone tries it

Runs on

An Expo development build or Expo Go app on a phone, or an emulator/simulator on a laptop. Also works on web (React Native Web) but the PoC targets phone.

Start

cd flock-calendar then npx expo start — opens Expo DevTools; press a for Android emulator, i for iOS simulator, or scan the QR with Expo Go on a phone.

Demo recording

Run the app, record the screen (emulator or phone), show: setup → calendar → tap date → day list → check off → reopen and it's still there. Upload the recording as the 1–3 minute demo video; push the repo to GitHub.

Deployment

Optional, not required. If Monday wants others to try it directly, Expo Application Services (EAS) or expo publish can host it; record target and steps in 6-ship. Reviewers won't clone or run code — the video is the proof.

Environment

Node.js, npx/bun, Expo CLI. No API keys.

Look and feel

Eco-friendly — greens, lemon, yellow. Defined as CSS variables in global.css, consumed via nativewind classes like bg-primary, bg-secondary, text-accent-foreground.

Typography: Inter (regular, medium, bold) via nativewind/preset font family tokens.

Mood: farm vibe, phone-first — plain, warm, readable, high-contrast enough for quick use outdoors. Spacious but not sparse; big tap targets.

Identity: bird logo (placeholder until an actual logo asset exists); clear calendar section and list section.

Stack constraint: nativewind on React Native supports most Tailwind utilities; web-only features (complex grid, backdrop filters) should be avoided.

Data model

Everything stored in AsyncStorage as JSON under a single key flock:v1. Where it lives: on the phone. How it gets updated: writes on setup, task completion, add batch/task. What happens when the user leaves and comes back: AsyncStorage loads on app open; calendar and day list re-derive from the stored rules.

Batch — id: string, label: string (e.g. "Batch A"), birdCount: number, hatchDate: string (ISO date; age is derived, not stored)

Rule — id: string, batchId: string, kind: 'checkup'|'feed'|'water'|'eggs'|'cleaning'|'vaccine'|'deworm'|'custom', title: string, intervalDays?: number (recurring), startOffsetDays?: number (hatch-relative like vaccines), durationDays?: number (multi-day like deworming), timesPerDay?: number (for feed/water/checkup)

Completion — ruleId: string, date: string (ISO date), doneAt: string (ISO timestamp)

Derived (not stored): the calendar grid — for any date, each rule answers "due today?"; hide anything already in completions for that date.

Important failure modes

AsyncStorage write fails

Show a plain message "Couldn't save — try again" and keep the task unchecked so it still shows on the list.

No data on first open

Show the setup questionnaire (by design, not an error).

Empty day (nothing due)

Show an empty list with an "add task" affordance (by design).

Bad date tapped

The day list renders empty; no crash.

What was simplified and why

→ Out for now click to expand
  • AsyncStorage single JSON file instead of a hosted database — same data shape, same queries, no infrastructure; the PoC is single-user and offline.
  • No AI model for schedule generation instead of an LLM-driven planner — the built-in standard poultry schedule is reliable and works offline; a wrong vaccine date is worse than no app.
  • No notifications/reminders instead of push notifications — the PoC proves the schedule, not delivery.
  • Month view calendar instead of a full date-picker library — proves the kernel with fewer dependencies.
  • Single caretaker, no accounts instead of multi-user sync — one phone, one farm.
